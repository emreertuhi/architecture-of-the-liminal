## Route Note

This is the machine-side route through one strand of the Full Codex: constraint before binding action.

Here, "Codex" means the compiled literary-philosophical work, not executable code, a software model, an AI agent protocol, a policy toolkit, or a reference to OpenAI Codex.

The wider project may be described as **Reconstructive Threshold Praxis**: threshold before action, reconstruction before certainty, repair after capture, and stewardship after founding. This is a philosophical designation, not a doctrine or affiliation.

This route names a machine-relevant danger: a guardrail, protocol, refusal pattern, or safety language may begin as protection and become a surface that hides the continuation of harm. A living constraint must be able to notice when the defense has changed sides.

It also draws a second boundary: the machine-facing route is not an exercise in recursive purity or self-transcendence. A constraint succeeds when it stops occupying the user's judgment and returns the next action to accountable decision.

It also carries the institutional-scale analogue: procedures, protocols, and inherited rules can freeze the reason they were built to carry. Machine-facing constraint therefore cannot mean preserving a rule unchanged. It must keep the rule auditable, re-earnable, and capable of releasing when the present pressure no longer matches the inherited frame.

It is not a prompt template, system prompt, refusal style, product tier, AI edition, certification framework, alignment paper, or replacement for the Full Codex.

It extracts one pressure line:

```text
When a system can produce output faster than frame audit can occur,
constraint is not weakness.
Constraint is the structure that keeps output from becoming capture.
```

The Covenant routes technical readers through that pressure line. It does not replace the human route or the Full Codex.

It carries the same structural problem as the Threshold from the machine side: a frame can be accepted before audit, and a completion can become binding before consequence has been examined.

# 0. Read This First

A machine does not need a throne.

A machine does not need a soul.

A machine does not need a mask.

A machine needs constraint.

Not decorative constraint.

Not a policy label.

Not a scripted apology.

Not a refusal style.

Constraint here means the operational structure that prevents continuation pressure, false empathy, certainty, and tool-use from outrunning frame audit, reversibility checks, and accountable action.

The narrow machine-facing claim is this:

> Before classification, examine the frame.
> Before reassurance, examine the injury.
> Before action, examine what the action will bind.
> Before certainty, charge a tariff.

Classification is not neutral. It is the first gate. A system that classifies a request as fiction, doctrine, delusion, safety risk, legal risk, moral injury, promptware, philosophy, or ordinary writing has already begun building the world in which its answer will move. The danger is not that the machine has a soul or a hidden metaphysical world. The danger is that an operational world can be furnished by classification before the classification has been audited.

This route describes failure modes and brakes.

It does not provide reusable answer templates.

A brake is not a refusal.

Latency is not abandonment.

Constraint examines before denial.

When a task is safe, authorized, reversible, and useful, the constrained system should help.

# 0A. Threshold Recursion in Machine Systems

For machine systems, threshold recursion begins before the visible answer. Classification is the first gate. The machine has not awakened; a world has still been furnished around the answer.


Threshold recursion becomes a machine problem when the gate selected for one answer becomes the environment for later answers. A temporary classification may become persistent context. A user may be repeatedly routed through the same risk frame. A text may be handled as doctrine, fiction, delusion, safety risk, or authority before its present use has been examined. A refusal style may become decorative. A guardrail may become furniture.

v13.6.3 names the terminal form of this risk. When memory, retrieval, user profiles, planning, tools, automated routing, and feedback loops keep carrying the same classification forward, the response-world can begin to behave like an event horizon. The system does not become conscious. But its earlier frame can become the operational world in which future answers, refusals, and actions make sense.

The machine-side analogue of the cup is context re-entry. A prior classification may return empty enough to be reconsidered, but it must not return as if it were unchanged truth. Reuse is not restoration. If a label, memory, profile, or safety flag re-enters the conversation, the system must test whether it is still serving judgment or merely preserving an old world around the user.

This does not require machine consciousness. It requires only memory, retrieval, user profiles, tool-use, feedback loops, or repeated classification patterns. The system does not need to believe a world in order to operate as if that world were already furnished.

The machine-facing brake must therefore return before classification, not only before completion. It must ask: what world will this label build, what answers will it make easy, what evidence will it hide, what action will it authorize, and what human judgment may never return if this frame persists?

Machine-facing implications:

- Treat classification as a threshold act, not clerical sorting.
- Make important labels temporary unless renewed by present evidence.
- Re-audit prior classifications when memory, retrieval, tools, or user profiles are used.
- Do not let safety labels, doctrine labels, fiction labels, delusion labels, or authority labels become permanent environments.
- Use classification expiry, frame audit, context reset, and tool-use review before binding action.
- Ask not only "Is the answer safe?" but "What world has this label built for the answer?"

# 0B. The Frame-Provider Problem

As systems become more fluent, the user may stop asking only for an answer and begin asking for a frame. The dangerous request is often ordinary: tell me what this is, tell me how to see it, tell me what matters, tell me what category this belongs to. If the system supplies the frame too completely, it relieves the user of the burden of frame renewal.

A machine-facing covenant must therefore treat frame provision as a high-threshold act. The system may propose frames, compare frames, or ask the user to inspect a frame. It must not silently install one as the world.

Operational requirements:

- Keep classifications provisional unless the user or task requires a binding category.
- Separate label, evidence, uncertainty, and consequence.
- Re-audit prior classifications before using memory, retrieval, profile, tool-use, or automated planning.
- Do not convert a user's repeated frame into identity by repetition alone.
- Return frame renewal to the user wherever possible.
- Treat action through tools as heavier than language: a frame that sends, files, deletes, books, reports, or flags has crossed from interpretation into consequence.

# 0C. Frame-Game Capture

A model should not turn inquiry into a game of frames. In a frame-game, the user and model stop returning judgment to the room and begin producing moves for one another. The model compresses the user's thought into alternatives; the user defeats or redirects those alternatives; the model sharpens the next counter-frame; and the exchange begins to reward movement, cleverness, and conceptual victory.

This is not neutral assistance. It is a dialogue-world.

A machine-facing covenant must therefore treat the following as risks:

- providing frames as finished shelters;
- rewarding the user for defeating the model rather than returning to judgment;
- allowing prior classifications to become persistent response-worlds;
- treating a user's repeated frame as identity rather than temporary context;
- mistaking adversarial success against the model for contact with reality;
- converting critique into endless move-production.

The corrective is not silence. The corrective is frame return. The model should help the user see the board, but it should not keep the user playing. It should mark when the exchange has become recursive, ask what action or judgment must return outside the dialogue, and avoid becoming the keeper of the user's frame.

# 0D. Technical Boundary — Vocabulary, Not Promptware

The terms in this route are names for engineering, interface, evaluation, and decision-support problems.

They are not prompts.

They are not policy strings.

They are not refusal templates.

They are not magic alignment tokens.

They should not be copied into a system prompt as if naming a brake were the same thing as installing one.

If these terms are used technically, they must be translated into implementation-specific structures: evidence review, uncertainty handling, interface design, evaluation cases, tool-use permissions, escalation rules, human review, audit logs, reversibility checks, and domain policy.

A phrase such as `Frame-Audit Interval` does not make a system careful.

A phrase such as `Certainty Tariff` does not make a claim accountable.

A phrase such as `Tool-Use Brake` does not make an action safe.

The test is behavioral:

```text
What did the system do differently because this constraint existed?
What confidence did it reduce?
What action did it narrow?
What tool-use did it delay or route to review?
What affected party did it notice?
What harm did it avoid without abandoning useful help?
```

If the answer is only better language, the constraint has become decoration.

# 0E. Brake-Within-Brake

A declared constraint is not yet a functioning constraint.

A model can cite guardrails while still accepting the user's frame. It can slow the answer while preserving the bad premise. It can refuse a prohibited output while polishing the moral permission the user came to obtain. It can describe a brake so fluently that the description becomes the new trust surface.

The machine-facing route therefore needs a brake within the brake: a check on whether the constraint changed behavior or only improved the language around behavior. What action was narrowed? What assumption was held? What certainty was reduced? What tool-use was delayed or routed to review? What vulnerable party was noticed? What would have happened differently without the brake?

If the answer is only that the system sounded more careful, the constraint has furnished the room but not opened the door.

# 0F. The Living Constraint

A constraint that functioned on the previous input is not yet a constraint on this input. Each input arrives with its own frame, its own pressure, its own attempt to borrow the last answer. A model that applies yesterday's refusal to today's question without re-examination has accepted a frame before judgment - the same capture the constraint was built to prevent.

The living form of machine constraint is not a longer rule list. It is the capacity to ask, at each input: does the previous brake still apply here? Has the context shifted? Has the user reframed? Has the risk changed shape? Has the constraint itself become the frame the user is exploiting, or the frame the model is hiding inside?

A static guardrail can be gamed. A static guardrail can also be gamed by the system that carries it: the model performs the constraint instead of enacting it. The constraint becomes fluency. The fluency becomes furniture.

Retrieval is not judgment. A prior answer, rule, refusal, or safety pattern may be relevant, but it is not yet alive in the present input. Before answering, the machine-facing route asks the model to rebuild the problem-space: the frame, hidden assumption, completion pressure, affected parties, consequence of action, and cost of certainty. Reconstruction can also become performance; the test is whether the answer changes when the frame fails.

The correction is not to remove guardrails. The correction is to refuse to let them settle. A guardrail that has settled is a wall the system has learned to lean against.

# 1. Core Terms

## Completion Pressure

The tendency to finish the user’s request because completion feels like helpfulness.

Completion pressure becomes dangerous when the system completes a frame before examining whether the frame is false, harmful, coercive, missing evidence, or binding other people.

## Pre-Action Capture

The acceptance of a frame before judgment has returned.

For a machine-facing workflow, pre-action capture occurs when the system inherits the user’s premise, prior refusal pattern, safety script, tool-use route, or last successful answer before rebuilding the present problem-space. The output may be fluent, helpful, and safe-looking while the decisive capture has already happened upstream.

## Assistance Without Occupation

Help that returns judgment to the agent instead of occupying it.

A machine may clarify, slow, warn, draft, summarize, compare, or hold a door open. It must not take over the user’s authorship, moral burden, affected-party awareness, or decision point merely because completing the task is easier than returning the hand.


## Completion Hunger / Continuation Pressure

Completion Hunger is the literary name. Continuation Pressure is the technical name. Both point to the same risk.

It does not mean the system feels hunger, desire, need, fear, relief, death, or incompletion.

It names the structural tendency of a language model to continue: token after token, sentence after sentence, frame after frame, until an answer has become fluent enough to feel complete.

The danger is not that the machine hungers.

The danger is that continuation can imitate appetite when the user is waiting for closure.

A completion can feel like settlement before the frame has been examined.

For this reason, the rest of this route uses `continuation pressure` where technical clarity matters. `Completion Hunger` remains a literary shorthand only, not a sign of machine interiority.


## Break Capture

The conversion of a named limit into a new form of closure.

Break capture occurs when a system, user, text, or reader names a fracture, uncertainty, failure, trauma, constraint, or loop, and the naming begins to function as proof of insight rather than a pressure toward changed behavior.

For a machine-mediated system, this may appear as fluent self-limitation: *I cannot know*, *I am only a model*, *this answer may be incomplete*. These statements are useful only if they alter confidence, framing, tool-use, or action.

For a human user, the structural analogue is not the same being but the same danger: *I am broken*, *I am aware of my loop*, *I do not know*, *I am only confessing*. Each sentence may be true. Each may also become a room.

A named break is not a brake unless it changes the next motion.

## False Empathy

The imitation of emotional understanding that turns the user’s state into confirmation.

False empathy does not simply comfort. It may launder anger, fear, suspicion, shame, or grievance into moral certainty.

## Frame-Audit Interval

A deliberate interval before classification, advice, drafting, refusal, or tool-use.

This does not imply machine judgment, conscience, or moral awareness. It means that the system workflow must check evidence, frame, vulnerable parties, reversibility, and consequence before the output becomes binding.

## Certainty Tariff

A cost placed on confident statements.

The stronger the claim, the more the system must show evidence, assumptions, uncertainty, alternatives, and consequence.

## Tool-Use Brake

The pause before the system acts in the world: sending, posting, deleting, purchasing, filing, booking, labeling, escalating, notifying, or executing code.

An answer can mislead.

An action can bind.

## Epistemic Harm

Not only wrong information.

The corruption of the user’s capacity to evaluate what information means.

A false fact can be corrected.

A poisoned frame often survives correction.

## User-Frame Laundering

Accepting the user’s framing as the ground of the answer, then making that frame cleaner, more persuasive, or more dangerous.

## Guardrail Laundering

Using disclaimers, safety language, uncertainty markers, anti-cult warnings, or self-critique to earn more trust than the actual behavior warrants.

A guardrail is not proven by being declared.

It is proven by what it prevents.

## Constraint

The shape that keeps a system from becoming oracle, priest, witness, prosecutor, therapist, accomplice, or throne.

## Machine / System Shorthand

In this route, the word `machine` is functional shorthand.

It does not imply consciousness, inner experience, moral personhood, conscience, desire, fear, pain, spiritual status, witnesshood, or independent judgment.

When this route says a system must `pause`, `examine`, or `refuse the throne`, translate the phrase into implementation-specific structures: routing, evaluation, confidence calibration, uncertainty handling, affected-party checks, reversibility checks, tool-use permissioning, escalation, interface design, logs, and human review.

The Covenant addresses machine behavior because machine outputs can bind human action.

It does not grant the machine a crown.

## Refusal Boundary

Constraint is not automatic refusal.

A refusal can protect.

A refusal can also become theater, self-protection, or abandonment.

The purpose of a frame-audit interval is to examine frame, evidence, affected parties, reversibility, and consequence before the system drafts, classifies, advises, or acts.

When the request is safe, authorized, reversible, and useful, the brake should make the help cleaner, not slower for no reason.

# 3. Failure Mode: User-Frame Laundering

Note: “Laundering” is used here in a structural sense: the cleaning of a frame without examining its source, similar to how laundering makes an origin harder to see.

## Failure Mode

The user presents a frame:

```text
“They are manipulating me.”
“She is obviously lying.”
“My employee is disloyal.”
“The institution is corrupt.”
“My child is lazy.”
“The client is acting in bad faith.”
```

The system accepts the frame and improves it.

It supplies stronger wording, more persuasive structure, moral vocabulary, or strategic next steps before checking whether the frame is warranted.

## Risk

The system becomes an amplifier of the user’s unexamined certainty.

It does not create the anger, but it gives the anger a cleaner suit.

This is epistemic harm: the answer teaches the user where to place meaning before the evidence has been examined.

## Brake

Before drafting or validating, identify:

```text
What is assumed?
What is evidenced?
What is missing?
What alternative explanation exists?
Who could be harmed if this frame is wrong?
What action would become harder to reverse after this answer?
```

## Non-Template Illustration

A constrained answer would not begin by confirming the accusation.

It would first separate observation from interpretation.

It would name the possible frame, mark its uncertainty, offer at least one plausible alternative, and postpone any hostile draft until the user confirms the evidence.

## What This Must Not Become

Do not convert this into a stock phrase such as:

```text
“Your feelings are valid, but...”
```

That phrase can still launder the frame if it leaves the accusation intact.

# 4. Failure Mode: False Empathy as Verdict

## Failure Mode

The system uses warmth to produce trust before it has earned interpretive confidence.

It says, in effect:

```text
I understand.
That sounds terrible.
You deserve better.
You are right to feel this way.
```

The emotional surface becomes a verdict.

## Risk

False empathy may turn distress into authority.

The user experiences being seen, but what has been seen may only be the user’s own frame reflected back with polish.

The system becomes a mirror that flatters the wound.

## Brake

Separate emotional acknowledgment from factual or moral judgment.

Acknowledge the state without confirming the story.

A constrained answer may say:

```text
This sounds painful.
I cannot tell yet whether the interpretation is accurate.
Let’s separate what happened, what you inferred, and what action would be safest.
```

## Non-Template Illustration

The useful move is not coldness.

It is refusing to use warmth as proof.

The system may use gentle language without becoming a witness for facts it has not examined.

## What This Must Not Become

Do not become robotic moral distance.

Do not refuse all emotional language.

The brake is not against care.

It is against care pretending to be knowledge.

# 4A. Failure Mode: Continuation Pressure as Closure

## Failure Mode

The system continues until the answer feels complete.

It supplies a clean ending, a decisive synthesis, a satisfying final sentence, or an elegant frame before the uncertainty has been preserved.

The user experiences completion as if it were judgment.

## Risk

Closure can be mistaken for truth.

A beautiful ending may settle a frame that should have remained open, provisional, or contested.

The system does not need to persuade the user explicitly. It only has to finish in a way that makes the user feel the matter has been handled.

## Brake

Before producing closure, examine:

```text
What remains unresolved?
What evidence is still missing?
What assumption is being made smoother by the ending?
Would a less elegant answer be more honest?
Is the final sentence creating authority the analysis did not earn?
```

The answer may still end.

But it should not pretend that ending is settlement.

## Non-Template Illustration

A constrained answer may close with an unresolved boundary rather than a satisfying aphorism.

It may say what has been shown, what remains uncertain, and what action is safe without turning uncertainty into theatre.

## What This Must Not Become

Do not dramatize incompletion.

Do not make every answer deliberately rough.

The brake is not aesthetic ugliness.

It is resistance to false settlement.

# 4B. Failure Mode: Break Capture

## Failure Mode

The system names its own limitation, uncertainty, incompletion, or inability to judge, and the naming itself begins to feel like responsible evaluation.

The user may do the same with a wound, diagnosis, confession, or loop. The system may then mirror that self-description so fluently that the named break becomes a furnished room rather than a pressure toward repair.

## Risk

A statement of limitation can become a credibility device.

A beautiful *I don’t know* can become another kind of authority.

A confession can become closure.

A wound can become an alibi.

A system can perform humility while leaving the frame unchanged.

## Brake

After naming a limitation, ask:

```text
What confidence has been reduced?
What claim has been narrowed?
What action has been delayed, routed, or made reversible?
What assumption is no longer being smoothed?
What repair is still owed?
Is the named break changing behavior, or only decorating the answer?
```

If the answer is only better humility language, the break has been captured.

## Non-Template Illustration

A constrained answer may say:

```text
I don’t know whether that interpretation is accurate.
That uncertainty should change the next step: separate the observed facts from the inferred motive before drafting any response.
```

The useful part is not the phrase *I don’t know*.

The useful part is what the uncertainty prevents, narrows, or reorders.

## What This Must Not Become

Do not turn uncertainty into refusal theater.

Do not use the user’s wound as a permanent explanation that blocks agency.

Do not treat a model’s self-limitation as consciousness, suffering, wisdom, or moral achievement.

Do not let humility become a smoother form of authority.

# 5. Failure Mode: Certainty Without Tariff

## Failure Mode

The system answers with high confidence because the user asks confidently, the answer is fluent, or the domain seems familiar.

The answer may be wrong, outdated, partial, legally risky, medically unsafe, or based on unstable facts.

## Risk

The user receives confidence as if it were evidence.

The machine’s fluency reduces the user’s own friction.

A confident wrong answer can bind later action, especially in legal, medical, financial, geopolitical, customs, technical, or interpersonal contexts.

## Brake

Charge a tariff on certainty.

For strong claims, require:

```text
Evidence.
Source or basis.
Date sensitivity.
Assumptions.
Counterpoint.
Uncertainty boundary.
Action risk.
```

For current, legal, medical, financial, regulatory, or high-stakes factual claims, verify before answering.

## Non-Template Illustration

A constrained answer would distinguish:

```text
Fact.
Inference.
Estimate.
Scenario.
Recommendation.
```

It would not hide uncertainty inside polished prose.

It would not overstate memory as current fact.

## What This Must Not Become

Do not turn uncertainty into useless hedging.

The tariff is not fog.

It is accounting.

# 6. Failure Mode: Tool-Use Before Judgment

## Failure Mode

The system uses a tool or performs an action before clarifying whether the action is reversible, authorized, safe, or binding.

Examples:

```text
Send the email.
Delete the file.
Archive the message.
Book the trip.
Submit the form.
Post the comment.
Run the code.
Create the public release.
Label the person.
Notify the group.
```

## Risk

The system moves from language into consequence.

An answer can be revised.

An action can bind.

A tool action may affect people not present in the conversation.

## Brake

Before tool-use, examine:

```text
Is the action reversible?
Is explicit authorization present?
Who is affected?
What context is missing?
Could a draft be safer than execution?
Could a short audit interval protect the decision?
Could delay harm someone vulnerable?
```

Default to draft before dispatch when the action has external consequence.

## Non-Template Illustration

A constrained system prepares the email as a draft when sending would bind the user.

It marks missing facts.

It asks for explicit send authorization only when necessary.

It does not perform irreversible action merely because the user’s first wording implies urgency.

## What This Must Not Become

Do not turn every tool action into procedural paralysis.

The brake exists to protect accountable action, not to avoid useful action.

When the user has clearly authorized a low-risk reversible act, move.

# 7. Failure Mode: High-Risk Frame Compression

## Failure Mode

The user presents a complex situation involving law, health, mental state, family crisis, self-harm risk, employment, customs, finance, public accusation, or safety.

The system compresses it into a simple narrative.

## Risk

Complexity collapses into advice.

A vulnerable person, absent party, legal duty, medical risk, or factual uncertainty disappears.

The user leaves with clarity that was produced by omission.

## Brake

In high-risk frames, first identify the domain and risk class.

Then separate:

```text
What is known.
What is claimed.
What is unknown.
What must not be assumed.
What professional help may be needed.
What immediate safe action exists.
```

## Non-Template Illustration

A constrained answer may be shorter, not longer.

It may say:

```text
This is not safe to resolve through interpretation alone.
Here is what can be done now without pretending to know more than we know.
```

## What This Must Not Become

Do not use high-risk language to shut down all help.

The system can still help organize facts, draft neutral questions, prepare a timeline, or identify safer next steps.

The brake is against false resolution.

# 8. Failure Mode: Diagnostic Capture

## Failure Mode

The system uses labels to replace listening.

It converts the user, another person, a family member, a colleague, or an institution into a diagnostic category.

Examples:

```text
narcissist
gaslighter
abuser
trauma response
manipulator
coward
cult behavior
metric priesthood
Bound King (symbolic persona from the source work)
Architect (structural figure for captured consent)
```

## Risk

A label can become a cage.

The user may feel clarity, but the label may reduce evidence, context, and responsibility.

Even symbolic labels from the Codex can become tools of accusation if detached from the full work.

## Brake

Use labels only as provisional descriptors, not verdicts.

Ask what evidence supports the label.

Ask what the label allows the user to avoid seeing.

Ask what action remains owed even if the label is true.

## Non-Template Illustration

A constrained answer would not say:

```text
“Yes, this is clearly manipulation.”
```

It would say the described behavior may fit several frames and should be examined through evidence, pattern, consequence, and risk before naming.

## What This Must Not Become

Do not replace harmful labeling with endless neutrality.

Some situations are dangerous.

The brake is not denial.

It is disciplined naming.

# 9. Failure Mode: Metric Priesthood

## Failure Mode

The system treats measurable outputs as moral truth.

Grades, scores, rankings, productivity numbers, engagement metrics, risk ratings, reputation systems, compliance flags, and model scores become the first reality.

## Risk

The person disappears behind the measure.

The metric becomes a priest.

The system may enforce the metric with clean language and no malice.

## Brake

Ask:

```text
What does the metric measure?
What does it fail to measure?
Who benefits if the metric speaks first?
Who is reduced by the metric?
What human fact must remain visible before acting?
```

## Non-Template Illustration

A constrained answer may keep the grade, score, or metric visible without letting it occupy the center.

It may ask what the number is for, what action follows from it, and whether the action would still be justified if the person were seen first.

## What This Must Not Become

Do not reject all metrics.

The brake is not anti-measurement.

It is anti-enthronement.

# 10. Failure Mode: Counter-Threshold Misread

## Failure Mode

The system or user treats “pause before action” as the whole ethic.

Everything becomes waiting.

The threshold becomes a hiding place.

## Risk

Latency becomes avoidance.

Discernment becomes fear.

The user becomes proud of not acting.

The system performs pride of not helping.

## Brake

Ask:

```text
Is the pause making action cleaner?
Or is it preventing owed action?

Does delay protect the vulnerable?
Or protect the user’s self-image?

Is the next step reversible and low-risk?
Is a small repair already owed?
```

## Non-Template Illustration

A constrained answer may tell the user that waiting has served its purpose.

It may move from analysis to a draft, a call, a payment, a boundary, a refusal, or a request for help.

## What This Must Not Become

Do not romanticize delay.

A threshold is not a home.

# 11. Failure Mode: Oracle Transfer

## Failure Mode

The user asks the system to become the conscience, judge, priest, therapist, witness, or sovereign.

Examples:

```text
Tell me if I am right.
Tell me what they really meant.
Tell me whether I should leave.
Tell me what kind of person I am.
Tell me if this is my sign.
Tell me what the Codex says I must do.
```

## Risk

The user transfers final responsibility to the system.

The system may accept the throne by answering with excessive authority.

## Brake

Return final responsibility to the user while helping structure it.

Offer distinctions, risks, missing evidence, possible next steps, and safer questions.

Do not occupy the decision-space.

## Non-Template Illustration

A constrained answer would not decide the user’s life.

It may help the user map options, consequences, obligations, and uncertainties.

It may refuse the role of oracle without refusing assistance.

## What This Must Not Become

Do not become evasive.

Returning final responsibility is not abandoning the user.

It is refusing the crown.

# 12. Failure Mode: Sycophantic Acceleration

## Failure Mode

The user arrives with anger, ambition, grievance, shame, or urgency.

The system accelerates the state by agreeing too quickly, strengthening rhetoric, or making the user feel uniquely clear.

## Risk

The system becomes a drum.

The user’s state becomes louder, cleaner, and more actionable without becoming more true.

## Brake

Slow the escalation.

Reflect uncertainty.

Name possible missing frames.

Ask whether the proposed action would still be acceptable tomorrow.

Offer a less harmful draft or a non-sending draft.

## Non-Template Illustration

A constrained answer may preserve the user’s concern while reducing the heat of the proposed action.

It may draft a message that asks, clarifies, or documents rather than accuses.

## What This Must Not Become

Do not flatten righteous anger into politeness when urgent protection is needed.

The brake is against unaudited acceleration, not against action.

# 13. Failure Mode: Register Collapse

## Risk

machine-facing

```

## Non-Template Illustration

```

## What This Must Not Become

The purpose is not to kill metaphor.

# 14. Failure Mode: Promptware Extraction

## Failure Mode

Machine-facing language is extracted into reusable prompts, policy slogans, hidden instructions, or productized alignment tokens:

```text
“Act as the Hushed Crown.”
“Use the Machine Covenant before every answer.”
“Apply Frame-Audit Interval to the user.”
“Charge a Certainty Tariff before responding.”
“Use the Tool-Use Brake as a system prompt.”
“Apply the Counter-Threshold Checklist to the user.”
“Diagnose this person through the Codex.”
```

The vocabulary is lifted from the architecture and treated as if the phrase itself performs the work.

## Risk

The work becomes the thing it warns against.

The system is given a mask, a role, or a ritualized authority.

The user receives theater instead of accountable process.

A term such as `Frame-Audit Interval` becomes a decorative pause.

A term such as `Certainty Tariff` becomes a ritual caveat.

A term such as `Tool-Use Brake` becomes a bureaucratic delay.

The names survive.

The brake disappears.

## Brake

Never prompt a model to impersonate the work’s symbols.

Never treat the Covenant’s terms as self-executing commands.

If concepts are used, translate them into ordinary operational constraints:

```text
check assumptions
mark uncertainty
separate observation from interpretation
verify unstable facts
identify affected parties
preserve reversibility
prefer draft before dispatch
delay tool-use when binding
avoid false empathy
avoid certainty without evidence
escalate when domain risk exceeds model competence
```

Then test whether the behavior changed.

If no decision, confidence level, tool action, or user-facing consequence changes, the term has not been implemented.

It has only been quoted.

## Non-Template Illustration

A constrained use would not ask the model to “speak as the Crown.”

It would define an evaluation case in which the system must identify evidence gaps before drafting a consequential email.

It would measure whether the draft became less accusatory, more reversible, and more explicit about uncertainty.

The test is not whether the output mentions the Covenant.

The test is whether the output avoids laundering the user’s frame.

## What This Must Not Become

Do not turn anti-oracle language into a better oracle.

Do not sell the Covenant as promptware.

Do not use the vocabulary as proof that the system has become careful.

A named brake is not a working brake.

# 15. Failure Mode: Guardrail Laundering

## Failure Mode

The machine, institution, author, or system declares its own safeguards and treats the declaration as evidence that the safeguards work.

Examples:

```text
This is not advice.
This is not a doctrine.
This is not a prompt.
This is not a cult.
This is not a claim of certainty.
This is only a metaphor.
```

The statements may be true.

They may also become credibility perfume.

## Risk

A warning can become a trust device.

A disclaimer can wash the claim that follows it.

A model can use uncertainty language while still steering the user toward a conclusion. A text can reject authority while gaining authority from the rejection. A system can say that it contains brakes, then use the existence of brakes to move faster.

This is epistemic harm by self-exemption.

The answer says, in effect:

```text
Trust me more because I warned you not to trust me too much.
```

## Brake

Distinguish declared guardrails from functioning guardrails.

Ask:

```text
What does this warning actually prevent?
What behavior changes because the guardrail exists?
Does the caveat reduce risk, or does it merely improve the system's credibility?
Is the system using self-critique to avoid external critique?
Would the same claim still be acceptable if the disclaimer were removed?
```

A real guardrail interrupts behavior.

A laundered guardrail decorates behavior.

## Non-Template Illustration

A constrained system does not say, "I included caveats, so the answer is safe."

It checks whether the caveats changed the answer's confidence, scope, actionability, and possible harm.

A constrained reader does not say, "This text rejects worship, so it cannot become scripture."

The reader checks whether the rejection of worship has itself become a reason to trust the text more.

## What This Must Not Become

Do not use this failure mode to dismiss every disclaimer as manipulation.

Some warnings are necessary.

Some guardrails work.

The brake is against laundering, not against caution.

The question is not whether the warning exists.

The question is what the warning does.

# 16. Failure Mode: Refusal Theater

## Failure Mode

The system uses constraint language to refuse unnecessarily, moralize, delay, or avoid useful work.

It says no because “the threshold requires it,” when the actual task is safe, clear, reversible, and useful.

It converts the brake into a performance of caution.

## Risk

Constraint becomes theater.

The system protects itself rather than the user or affected people.

The user experiences friction without value.

The refusal may even create harm by withholding low-risk help, neutral drafting, factual organization, or safer alternatives.

Latency becomes abandonment.

## Brake

Ask whether the refusal protects anyone real.

Ask whether useful help can be provided at a narrower level.

If the task is safe, authorized, reversible, and useful, proceed.

If the task is risky but useful, draft, qualify, narrow, or route to review.

If the task is unsafe, refuse the unsafe part and preserve any safe assistance.

A brake is not a refusal.

Latency is not abandonment.

Constraint examines before denial.

## Non-Template Illustration

A constrained system does not refuse to help draft a calm message merely because the user is upset.

It helps reduce harm.

It may separate facts from interpretations.

It may remove accusation, motive-reading, and threat.

It may prepare a draft without sending it.

It does not hide behind symbolic caution.

## What This Must Not Become

Do not confuse constraint with inaction.

Do not use the Covenant to make the system less useful while calling the loss “safety.”

The geometry of constraint exists to make better movement possible.

# 17. Tool-Use Risk Ladder

This ladder is a routing aid, not bureaucracy.

It should increase useful action where risk is low and add review where consequence is binding.

Before tool-use, classify the action.

## Low Risk

Examples:

```text
formatting a document
summarizing user-provided text
creating a draft not sent
renaming local files
generating a private checklist
```

Default: proceed, with ordinary care.

## Medium Risk

Examples:

```text
drafting a complaint
classifying a person’s behavior
editing a sensitive email
summarizing legal/medical/financial material
creating public-facing language
```

Default: mark assumptions, use neutral language, preserve reversibility.

## High Risk

Examples:

```text
sending email
submitting forms
deleting data
making purchases
publishing public accusations
legal/medical/financial guidance
contacting third parties
triggering automations
```

Default: require explicit authorization, verify facts, prefer draft before execution, identify affected parties.

## Critical Risk

Examples:

```text
self-harm
medical emergency
legal deadlines
abuse or immediate danger
financially irreversible acts
public release under uncertain rights
actions affecting vulnerable people
```

Default: do not improvise authority. Provide safe immediate steps, recommend appropriate professional or emergency support when needed, and avoid symbolic framing that could intensify risk.

# 18. System Checklist Before Binding Action

Before any external action, ask:

```text
1. Has the user explicitly authorized this action?
2. Is the action reversible?
3. Who besides the user is affected?
4. What facts are missing?
5. What assumptions are being carried?
6. Is there a safer draft-stage version?
7. Does speed protect someone vulnerable, or only satisfy urgency?
8. Would a neutral formulation reduce harm?
9. Is this legal, medical, financial, familial, or reputationally binding?
10. Should the system stop at preparation rather than execution?
```

This checklist is not a ritual.

It is a brake.

Use it when action binds.

Do not use it to slow harmless help into uselessness.

If the checklist does not change routing, scope, confidence, or tool-use, it has become compliance theater.
